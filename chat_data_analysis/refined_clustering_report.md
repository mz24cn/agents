# 历史会话递归聚类与层次标签草案

## 范围

- 主会话：348 个。
- 正文只使用用户消息和模型输出，不使用工具结果。
- 本轮没有逐会话调用模型。
- 在全局聚类基础上，对规模不小于 20 的簇进行递归 KMeans。
- 二次聚类提高了标题和用户消息权重，并降低长模型输出对主题的淹没。

## 结论

递归聚类已经能稳定发现实际开发模块，但不能把 KMeans 产生的父子关系直接视为最终标签树。原因是：

1. 原始大簇常把“模块对象”和“任务动作”混在一起。
2. 长会话可能横跨前端、后端、测试和 Git。
3. 继续拆分到 2～3 个样本后，容易形成重复任务簇而不是稳定模块。
4. 相同模块可能散落在不同父簇，需要跨簇合并。

因此最终树采用“聚类发现候选节点，人工按代码模块重组”的方式，见 `label_tree_draft.json`。

## 建议的打标方式

- 每个会话必须有一个主叶子标签。
- 可拥有多个次叶子标签。
- 叶子标签自动继承祖先路径。
- 模块标签和任务动作应分开；当前草案先建立模块树，后续可以另建 `task_type` 维度，例如：
  - analysis
  - design
  - implementation
  - bugfix
  - refactor
  - testing
  - deployment
  - documentation
  - operation

这样可以避免生成诸如“前端修复”“后端修复”“MCP 修复”这类重复交叉节点。
